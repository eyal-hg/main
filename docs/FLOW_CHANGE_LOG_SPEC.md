# לוג שינויים בתזרים — מסמך אפיון

*HK · אוגוסט 2026 · אפיון למפתחים*

---

## 1. הבעיה

> "למה פתאום יש לי חריגה עוד שבועיים? אתמול לא היה."

היום התשובה דורשת ממנהל התזרים לחפור ידנית, ולא תמיד הוא מצליח להבין. התחזית מתעדכנת בכל שאיבה, אבל **אף אחד לא רושם מה השתנה בין עדכון לעדכון** — יש לנו תמונת מצב, אין לנו היסטוריה של השינויים.

**מה המערכת צריכה לדעת לענות:**

1. מה השתנה בתחזית **לתאריך מסוים** (לא "בכלל") מאז אתמול / מהשבוע / מהפגישה האחרונה
2. **למה** — רשימת האירועים שגרמו לזה, מדורגת לפי השפעה
3. גם כשאין חריגה — "מה בכל זאת השתנה"
4. להתריע **יזומה** ברגע שנוצרת חריגה שלא הייתה, בלי שאף אחד יפתח מסך

## 2. עקרונות יסוד

**א. שני צירי זמן.** לכל אירוע יש שני תאריכים שאסור לבלבל ביניהם:

| ציר | שדה | משמעות |
|---|---|---|
| **מתי נרשם** | `ts` | מתי גילינו את השינוי (זמן הריצה) |
| **מתי הכסף זז** | `value_date` | התאריך שהתנועה משפיעה עליו — `date` בתנועה |

השאלה "מה השתנה מאתמול" מסננת לפי `ts`. השאלה "מה משפיע על 24.08" מסננת לפי `value_date`. הווידג'ט משלב את שתיהן.

**ב. הדלתא היא עקומה, לא מספר.** תשלום שזז מ-12.08 ל-22.08 לא "הוריד את התזרים ב-19,800" — הוא יצר **בור זמני** בין 12.08 ל-22.08, ואחריו הכל חוזר למקומו. לכן אי אפשר להציג מספר אחד; חייבים לשאול **לאיזו נקודה על הציר** מסתכלים.

**ג. הפירוק שסוגר את החשבון.** התחזית ליום D מורכבת משני חלקים בלבד:

```
תחזית(D) = יתרה נוכחית + Σ תנועות עתידיות עד D
```

ולכן השינוי מתפרק בדיוק לשניים, בלי חפיפה ובלי חורים:

```
Δתחזית(D) = Δיתרה נוכחית + Δתנועות עתידיות עד D
```

- **Δיתרה נוכחית** — מה קרה בבנק. הדבר היחיד שמזיז אותה: תנועות חדשות שכבר בוצעו.
- **Δעתיד** — מה השתנה בצפי: נוסף / נמחק / סכום / תאריך זז.

זה גם סדר החישוב וגם מבנה ההסבר למשתמש.

**ד. שום שקל לא זז בלי שורה בלוג.** כל דלתא חייבת להתאזן מול האירועים שמסבירים אותה. שארית לא מוסברת נרשמת כאירוע מפורש (`balance_sync`) ולא נעלמת בשקט.

## 3. הצנרת — איפה הלוג נכנס

```
ביזיבוקס → raw_data (hash: נכתב רק כשיש שינוי)
              ↓
         בניית process_data (שוטף + 3 חודשים)
              ↓
    ┌─── כאן הלוג ───┐   ← הנקודה היחידה שמחזיקה ביד את raw ישן/חדש + process ישן/חדש
    │  diff + סיווג   │
    │  + בקרת יתרה    │
    └────────┬────────┘
             ↓
   כתיבה: process_data (נדרס)  +  flow_change_sets (append-only)
             ↓
   צרכנים: ווידג'ט · מסך לוג · התראה · AI · הודעה בקבוצה
```

**למה כאן ולא על ה-raw:** הצרכנים מדברים בשפת יתרות ("התחזית ל-24.08 ירדה ב-32,400 ונכנסת לחריגה"), לא בשפת תנועות. לוג ברמת ה-raw היה מאלץ כל צרכן להריץ מחדש את החישוב.

**למה טבלה נפרדת ולא שדה בתוך `process_data`:** ה-process נדרס בכל בנייה ונקרא בכל בקשה. הלוג חייב להצטבר, ואסור שייגרר בכל קריאה.

## 4. מקור הנתונים

טבלת `bizibox_monthly_transaction_snapshots` — snapshot פר **חברה × חודש (`year_month_key`) × scope (`account_scope_key`)**, עם `transactions` jsonb ו-`transactions_hash` עליו.

מבנה תנועה (השדות הרלוונטיים):

| שדה | שימוש בלוג |
|---|---|
| `trans_id` | **מפתח הזהות** — עליו נשען כל הדיף |
| `date` (ms) | ה-`value_date` |
| `debit` / `credit` | הסכום והכיוון |
| `trans_time_type` | `past` / `future` — הציר בפועל/צפי |
| `isCashFlow` | האם התנועה בכלל בתזרים — **החלפת הערך משנה את העקומה** |
| `category` / `category_name` | קיטלוג — משנה דוחות ותקציב, **לא** את העקומה |
| `is_ccard` | אשראי — לא נוגע בעו"ש עד יום החיוב |
| `company_account_id` / `account_number` | החשבון |
| `asmachta` / `reference_number` | לאיתור והתאמה |

### 4.1 שתי מלכודות שחייבים לטפל בהן

**מלכודת א׳ — דיף חודשי מפספס הזזות תאריך.** תנועה שזזה מ-28.08 ל-03.09 עוברת בין **שורות snapshot שונות** (`year_month_key` שונה). דיף חודש-מול-חודש יראה "נמחקה מאוגוסט" + "נוספה בספטמבר" — שני אירועים במקום הסיפור האמיתי.

**החובה:** לאחד קודם את כל שורות ה-snapshot של החברה בכל החלון (כל החודשים, כל ה-scopes) למפה אחת `trans_id → transaction`, ורק אז לעשות דיף בין המפה הישנה למפה החדשה.

**מלכודת ב׳ — הטווח מתגלגל.** אתמול הטווח הסתיים ב-11.11, היום ב-12.11. תנועה ב-12.11 "נכנסה" לתחזית בלי ששום דבר השתנה. חישוב על טווחים שונים ייצור אירועי רפאים.

**החובה:** להשוות על **חלון קבוע** (החיתוך של שני הטווחים). תנועות שנכנסו רק בגלל התגלגלות הטווח מסומנות `horizon_entry` ולא נספרות כשינוי.

## 5. אלגוריתם הריצה

### שלב 0 — הכנה
1. טעינת ה-snapshots החדשים והקודמים של החברה לכל החלון.
2. בניית שתי מפות `trans_id → transaction` (ישנה / חדשה), מאוחדות על פני חודשים ו-scopes.
3. קביעת חלון ההשוואה הקבוע (חיתוך הטווחים) ו-`today`.

### שלב 1 — Δיתרה נוכחית (מה קרה בבנק)
1. איתור כל התנועות ב-`trans_time_type = past` שקיימות במפה החדשה ולא בישנה.
2. סיווג כל אחת מול הצפי:
   - יש צפי תואם שנעלם/התכווץ → **`executed`** (בוצע). אם הסכום שונה מהצפוי → **`actual_vs_forecast`** עם הסטייה.
   - אין צפי מולה → **`unexpected`** (לא צפויה).
3. **בקרה:** `Δיתרה` (מתוך `accounts`) חייב להשתוות ל-Σ התנועות החדשות **בחשבונות בנק בלבד** (`is_ccard = false`). שארית ≠ 0 → אירוע **`balance_sync`** עם ההפרש.

> **אשראי:** עסקאות `is_ccard` מצטברות ולא נוגעות בעו"ש עד יום החיוב, ולכן אינן חלק מבקרת היתרה. החיוב המרוכז הוא תנועה עתידית רגילה שחיה בשלב 2.

### שלב 2 — Δעתיד (מה השתנה בצפי)
דיף לפי `trans_id` על `trans_time_type = future` בתוך החלון הקבוע:

| מצב | סוג אירוע | משפיע על העקומה |
|---|---|---|
| `trans_id` חדש | `forecast_added` | ✔ |
| `trans_id` נעלם | `forecast_removed` | ✔ |
| `date` שונה | **`date_moved`** | ✔ (בור זמני) |
| סכום שונה | `amount_changed` | ✔ |
| `isCashFlow` התהפך | `cashflow_toggled` | ✔ |
| `category` שונה בלבד | `recategorized` | ✘ (דוחות/תקציב) |

אירועים שלא משפיעים על העקומה נרשמים בלוג עם `affects_curve = false` — הם מופיעים בלוג המלא ולא בחישוב הדלתא.

### שלב 3 — אירועי זמן (בלי שינוי בנתונים)
טריגר מעבר יום, שלא תלוי ב-hash:
- צפי שהתאריך שלו עבר ואין בפועל מולו → **`overdue`** (נגררת). לא הקטין את היתרה (לא קרה) ולא נעלם מהעתיד (עדיין צפוי).
- הגיע יום חיוב אשראי (`is_cycle_date`) → **`ccard_cycle`**.

### שלב 4 — בניית העקומה והדגלים
1. `curve_delta[D] = Σ delta של כל האירועים עם affects_curve ו-value_date ≤ D` — נשמר דחוס: רק תאריכים שבהם הערך משתנה.
2. **בקרה שנייה:** `curve_delta[D]` חייב להשתוות להפרש בין ה-`process_data` החדש לישן באותו יום. אי-התאזנות = באג בעיבוד, נרשם ונזרק להתראת ניטור.
3. חישוב `flags` (ראה 6.3) — **בזמן הכתיבה**, לא בזמן הקריאה.

### שלב 5 — כתיבה
`flow_change_sets` + `flow_change_events` (append-only), ורק אז דריסת `process_data`.
אם אין אף אירוע משמעותי — לא נכתבת שורה.

### 6.1 `flow_change_sets` — שורה לכל ריצה שהניבה שינוי

| עמודה | טיפוס | הערות |

### 6.2 `flow_change_events` — שורה לכל אירוע

טבלה שטוחה ולא jsonb, כי השאילתה המרכזית היא *"כל האירועים בחלון W שמשפיעים על תאריך ≤ D, מדורגים לפי |delta|"* — זה SQL פשוט.

| עמודה | הערות |
|---|---|
| `change_set_id` | FK |
| `company_id`, `ts` | לסינון חלון |
| `trans_id` | קישור לתנועה |
| `event_type` | מהטבלאות בשלב 1–3 |
| `value_date` / `value_date_prev` | הציר השני. שניהם ב-`date_moved` |
| `amount` / `amount_prev` / `delta` | `delta` חתום |
| `affects_curve` | bool |
| `account_id`, `is_ccard` | |
| `description`, `category_name` | לתצוגה |
| `asmachta` | לאיתור |

**שמירה:** 12 חודשים. האירועים קטנים; הנפח זניח.

### 6.3 `flags` — מחושבים בזמן הכתיבה

```json
{
  "worst_date": "2026-08-24",
  "worst_delta": -32400,
  "new_overdraft":      { "date": "2026-08-24", "was": 12150, "now": -20250 },
  "resolved_overdraft": null,
  "top_event_id": "…",
  "total_delta_30d": -18900
}
```

**למה בכתיבה ולא בקריאה:** כך ההתראה היא **אירוע** ולא שאילתה — "נוצרה חריגה ב-24.08" נדלקת ברגע הריצה ויוצאת ליועץ/למנהל, במקום לחכות שמישהו יפתח מסך. `resolved_overdraft` חשוב לא פחות: חריגה שנעלמה היא בשורה טובה שצריך לספר.

## 10. שאלות פתוחות — לבירור לפני קוד

1. **`trans_id` במעבר צפי→בפועל** — נשמר או נולד חדש? אם נשמר, `executed` נופל מהדיף מאליו. אם נולד חדש, צריך התאמה (סכום קרוב + תאריך קרוב + אותה קטגוריה/חשבון), אחרת כל תשלום שהתממש ייספר כשני אירועים: "צפי נמחק" + "הוצאה חדשה".
2. **האם נכתבת שורת snapshot בכל ריצה או רק כשה-hash משתנה?** קובע אם צריך לסנן לפני הדיף.
3. **מה יש ב-`accounts` jsonb** — יתרות פר חשבון? זה מקור בקרת היתרה.
4. **`account_scope_key`** — אילו ערכים, והאם אותה תנועה יכולה להופיע בשני scopes (סכנת ספירה כפולה באיחוד).
5. **מחיקה** — התנועה באמת יורדת מה-jsonb או מסומנת?
6. **`is_cycle_date`** ברמת ה-snapshot — מה בדיוק מסמן, והאם ממנו נגזר יום חיוב האשראי.
7. **הצפי (הצביעה קדימה)** — מגיע באותם snapshots כ-`future`, או ממקור נפרד? אם נפרד, צריך את אותו דיף גם עליו.
